# 开发与集成计划

## 1. 依赖关系

正式比赛执行存在严格先后顺序，但开发阶段应依靠稳定接口并行推进。

```text
平台 / 命名空间 / TF / 安全
  |-------------------|--------------------|
  v                   v                    v
SLAM + 自主探索     ArUco感知          Nav2机器人执行器
  |                   |                    |
  +------ map TF -----+                    |
              v                            |
       Task 1融合目标                       |
              |                            |
              +---- Task 1冻结输出 --------+
                              v
                    已保存地图上的定位
                              v
                    多机器人救援协调器
                              v
                           Task 2A
                              v
                LLM计划 -> 验证器 -> 调度器
                              v
                           Task 2B
```

正式运行中的硬性门槛：

1. Task 1输出必须在Task 2交接前冻结。
2. 机器人完成定位后才能参与Task 2分配。
3. 目标必须出现在Task 1冻结列表中，才有资格获得Task 2基本救援分数。
4. Task 2A必须停止并完成结果确认，才能进入Task 2B。
5. Task 2B任务计划通过验证后，才能触发任何由该计划产生的机器人动作。

Task 1结果不完整并不会在规则上绝对禁止进入Task 2，但组织方不会补充缺失的地图或目标，因此它实际上是影响得分的关键前置门槛。

## 3. 阶段1——并行建立各模块基线

### P1

- 为现有机器人增加命名空间。
- 同时启动两台仿真机器人。
- 建立静态地图定位、Nav2和安全停车。

### P2

- 使用模拟导航动作开发自主Frontier探索。
- 定义地图完成条件和质量指标。
- 决定并测试单机器人或双机器人建图模式。
- 建立阶段管理、`run_id`、运行目录、日志器和Task 1原子冻结骨架。

### P3

- 使用录制或合成Marker图像开发检测器。
- 发布模拟时间戳观测并融合为目标注册表。
- 验证持久化目标列表Schema。
- 对候选本地模型进行边缘设备可行性测试，并生成候选`MissionPlan`。

### P4

- 使用模拟机器人状态和执行动作开发分配器及救援状态机。
- 测试普通和协同救援的停留重置行为。
- 实现任务计划Schema、目标ID、能力和DAG可执行性验证器。

### P5

- 维护共享接口变更记录、CI入口和系统测试框架。
- 准备里程碑验收模板、发布清单和规则TBD索引，不实现生产运行节点。

退出条件：每个组件使用模拟接口通过本角色验收测试。

## 4. 阶段2——Task 1集成

集成顺序：

1. P1 + P2：把真实`scan/odom/TF`接入SLAM和自主导航目标。
2. P1 + P3：完成相机标定、光学坐标系、时间戳和目标观测。
3. P2 + P3：地图变化过程中，在正确观测时间完成TF转换和目标融合。
4. P2 + P3：原子化冻结Task 1并生成所有输出文件；P5仅在里程碑时独立复核。
5. P1 + P2：重新加载地图，并从变化后的起点重新定位。

退出条件：

- 不使用遥控或重复人工导航点。
- 在全新未知场景运行中生成地图和目标列表。
- 重复观察最终只生成一个目标。
- 输出文件可重新加载并通过Schema验证。
- 第二台机器人能够接入，接口不冲突且状态可见。

继续完成阶段3中的一次普通救援后，即构成比赛要求的端到端里程碑基线。

## 5. 阶段3——Task 2A集成

集成顺序：

1. P1发布定位和健康状态，并执行救援动作。
2. P3根据冻结目标注册表生成救援位姿。
3. P4分配一个普通目标，并验证停留和完成条件。
4. 加入导航失败或机器人故障后的重新分配。
5. 加入双机器人协同分配、先到等待、同步停留和计时重置。
6. P2验证事件持久化、阶段冻结和回放。
7. P5使用既定命令独立复核一次里程碑证据，不参与运行时实现。

退出条件：

- 至少一个普通救援能够自主完成。
- 至少一个协同目标由两台不同机器人完成。
- 故障注入后，不会出现机器人在没有有效安全命令时继续运动。
- 冻结阶段能够停止全部机器人并保留不可变结果。

## 6. 阶段4——Task 2B集成

1. P3在调Prompt之前建立带版本的自然语言测试集。
2. P3强制LLM输出符合任务计划Schema的候选结构化数据。
3. P4拒绝未知目标、循环依赖、矛盾任务和不可执行计划。
4. P4只把通过验证的任务步骤交给现有调度器。
5. 验证顺序执行、并行执行和多个前置条件。
6. Task 2A已经完成的目标可作为Task 2B新动作再次执行，但不能重复获得基本救援分数。
7. 保存原始指令、模型及版本、原始输出、验证计划、执行事件和最终结果。

退出条件：完整流程可以断网运行，并且不需要人工修正解析结果。

## 7. 阶段5——鲁棒性与比赛演练

测试矩阵包括：

- Task 1使用1/2台机器人；硬件允许时，Task 2使用2/3/4台机器人。
- 节点重启、延迟启动、通信中断和定位丢失。
- 错误、重复或延迟到达的Marker观测。
- 导航受阻、目标取消和机器人重新分配。
- 协同机器人提前到达、离开救援区或发生故障。
- 阶段超时、冻结、急停和恢复流程。
- 格式错误、歧义、循环依赖和不可执行的LLM指令。
- 干净机器安装和完全离线启动。
- 多次完整运行以及输出文件和哈希校验。

发布门槛：

- 连续三次完整演练不需要人工修复系统状态。
- 所有安全测试通过。
- 所有得分相关文件通过校验。
- 至少一名非负责人能够执行比赛运行手册。
- 选定模型和全部依赖已经离线准备完毕。

## 8. 集成规则

- 每周进行纵向端到端集成，不能等所有单独模块“全部完成”后才集成。
- 模拟模块必须使用真实接口类型和真实失败语义。
- 接口消费方必须测试错误、重复和过期的生产方输出。
- 每次运行都由一个启动配置固定所有组件和参数版本。
- 影响其他负责人的修改，必须由相关负责人审核后才能合并。
- 比赛行为不能依赖RViz、开发者终端、互联网或人工发布导航点。
- 已知故障必须转化为自动测试或明确的现场检查步骤。
