# 五人分工、职责边界与交接协议

状态：团队工作协议 v0.1

P1～P5是稳定的角色编号，不代表职位高低。团队确认后，在
`config/team_assignments.yaml`中填写姓名和备份人员。每个人不仅负责写代码，还要负责其模块的配置、测试、使用说明、故障处理和比赛现场操作手册。

## 工作量分配原则

- P1～P4各承担约22.5%的计划工作量，分别拥有一条完整的生产功能链路。
- P5承担约10%的计划工作量，定位为轻量的接口治理和独立验收角色，不拥有比赛运行时生产节点。
- 百分比用于规划任务数量和复杂度，不用于精确统计工时；每周根据未完成交付物复核一次。
- P5的审核只约束共享接口变更和里程碑发布，不作为P1～P4日常模块开发、Mock联调或分支测试的前置条件。
- 若P5临时无法参与，已冻结的接口版本仍可继续开发；由两名受影响模块负责人代行发布审核，但必须补记审核结果。

| 角色 | 计划占比 | 独立拥有的主链路 | 明确移出的工作 |
|---|---:|---|---|
| P1 | 22.5% | 机器人模型/驱动 → 定位/Nav2 → 安全动作执行 | 探索决策、目标融合、机器人分配 |
| P2 | 22.5% | SLAM/探索 → 阶段控制 → 冻结、Manifest和运行记录 | 感知、LLM、救援调度 |
| P3 | 22.5% | 图像检测/融合 → 目标导出；自然语言 → 候选计划 | DAG验证、机器人选择和执行 |
| P4 | 22.5% | 候选计划验证 → 任务分配 → 普通/协同救援验证 | LLM推理、底层导航和阶段管理 |
| P5 | 10% | 接口版本 → 独立验收 → 发布包 | 所有比赛运行时生产节点和模块代修 |

## 1. 全员统一的“完成”定义

一项工作只有同时满足以下条件，才可以标记为完成：

1. 输入、输出、坐标系、时间戳、单位、QoS和错误行为已有文档。
2. 仿真和实机使用相同算法接口，只允许驱动、标定及启动参数不同。
3. 正常输入、错误输入、超时、重启、取消和急停均有测试或可重复步骤。
4. 参数由配置提供，注明单位、范围和来源；不得把比赛TBD值写死。
5. 与得分有关的判断都有`run_id`、时间戳和可查询的原因记录。
6. 至少一名非模块负责人可以按照说明启动并验证该功能。
7. 数据生产方和消费方都确认接口语义正确，而不仅是“能看到Topic”。

任何模块不能以“Topic存在”“RViz里看起来正常”或“负责人电脑上运行过”作为集成完成的唯一依据。

## 2. P1——机器人平台、定位、导航与安全负责人

### 核心目标

提供稳定的单机器人执行底座：接收经过验证的探索点或救援点，安全到达，并持续向边缘节点报告可信状态。

### P1负责

- 仿真与实机两套启动配置及硬件抽象。
- `robot_1`～`robot_4`命名空间和机器人局部TF前缀。
- 电机、编码器、IMU、LiDAR、RGB-D及Phidgets相关驱动接入。
- URDF/Xacro中的车体尺寸、轮径、轮距、相机和LiDAR外参。
- 里程计以及最终选用的IMU/编码器融合配置。
- 已保存地图上的定位、初始定位和机器人被重摆后的重新定位。
- Nav2代价地图、规划器、控制器、恢复行为和取消行为。
- 每台机器人的`ExecuteRescueTask`动作服务器：只负责到达救援位姿并保持静止，不计时、不判定完成。
- 每台机器人的`relocalize`服务（全局定位、已知起点、位姿提示三种模式）。
- 速度指令看门狗、零速度停车、通信中断安全模式及急停。
- `/<robot_id>/state`状态发布和机器人本地诊断。
- 比赛和中期检查用的仿真场地（Gazebo世界）：按组织方场地图搭建外墙、内墙、障碍物和起始区，坐标原点与组织方坐标一致；机器人出生点和起点配置；ArUco标记模型由其负责人提供后放入世界（第11节G1、C3）。
- 演示前可行性检查：救援范围能否同时容纳所需机器人、各标记能否从可到达位置被相机看到（第11节G4）。
- 仿真中的碰撞检测与记录：与其他机器人、墙、障碍物和标记支架的接触，供结果验证使用（第11节G9）。

### P1不负责

- 选择下一个探索前沿。
- 判断ArUco目标的最终地图坐标。
- 决定哪台机器人执行哪个救援目标。
- 解析自然语言任务。

### P1的输入与输出

输入：实测机器人几何/标定、P2地图及阶段/冻结状态、P2/P4目标位姿，以及官方速度和安全参数。

输出：命名空间隔离的传感器/里程计/TF/导航接口；含位置协方差、健康状态、当前模式和活动任务的`RobotState`；动作反馈；以及`TF_STALE`、`LOCALIZATION_LOST`、`NAV_ABORTED`、`COMMAND_TIMEOUT`、`ESTOP_ACTIVE`等明确故障码。

### P1验收条件

1. 可通过配置生成1～4台机器人，而不需要手工修改Topic名。
2. 两台仿真机器人同时运行时，Topic和局部TF树不冲突。
3. 机器人被移动到新起点后，能通过`relocalize`在保存地图上重新定位，失败时返回明确原因而不是报告已定位。
4. 一组代表性导航点能够稳定到达；失败、取消或超时后一定输出零速度。
5. 边缘节点失联或进入冻结阶段后，在配置的安全时限内停车。
6. P4只调用`ExecuteRescueTask`即可执行/取消救援，不直接操作机器人内部Nav2。

### P1必须完成的交接

- 与P2确认`map/odom`发布权、未知区域策略和探索目标取消机制。
- 与P3确认相机内外参、光学坐标系和时间同步。
- 与P4确认动作状态、机器人可用性、取消语义和故障处理。
- 与P2确认启动就绪检查、阶段切换、冻结和运行日志。
- 向P5提供安全、导航和故障注入的独立验收证据。

## 3. P2——SLAM、探索与比赛控制面负责人

### 核心目标

让Task 1在无人给中间导航点的情况下完成有效探索，并管理比赛阶段、冻结和运行产物，使Task 1结果能可靠交接到Task 2。

### P2负责

- SLAM Toolbox参数、生命周期和地图质量评估。
- Frontier或其他自主探索算法。
- 探索目标选择、不可达前沿黑名单、重试和结束判断。
- 一台或两台机器人的探索协调。
- 采用两台机器人同时建图时的坐标对齐和地图融合方案。
- Task 1期间全局`map`坐标系发布权。
- 地图保存、元数据校验、重新加载和版本管理。
- 已探索面积、未知区域、剩余前沿及结束原因统计。
- 全局`run_id`、`CompetitionState`、阶段序号和阶段切换服务；按跳转表区分操作员和自主模块请求。
- 运行模式（`run_mode`）参数解析和比赛模式必需官方参数门禁。
- `/competition/request_reset`重置流程及交接、重置、重摆后的`relocalize`编排。
- `events.jsonl`、`manifest.json`、`component_versions.json`按`schemas/`写盘。
- Task 1原子冻结：协调地图与目标版本，生成Manifest并拒绝不一致输出。
- 运行目录、组件版本、JSONL事件、Rosbag、文件哈希及赛后导出。
- 全局启动顺序、就绪汇总和冻结/停止编排；机器人本地安全仍由P1负责。

### P2不负责

- 底层路径跟踪、电机控制和安全急停。
- 图像中的ArUco识别。
- Task 2机器人救援分配。
- LLM指令解析。

### P2的输入与输出

输入：P1的LiDAR、里程计、TF、时钟、导航动作和健康状态；比赛地图/时间配置；必要时P3提供的自动观察视角建议。

输出：实时统一地图、`map -> robot_N/odom`、探索目标、覆盖率和结束原因、地图图像/YAML/元数据、权威比赛阶段、Manifest和运行记录，以及TF中断、地图重影或轨迹不一致等故障。

### P2验收条件

1. 单机器人能自主探索，不依赖遥控或连续人工目标点。
2. 结束依据覆盖率、剩余前沿和超时等配置，而不是只能人工停止。
3. 地图中外墙和主要障碍物完整，没有严重重影或断裂。
4. 地图可重新加载，并可由P1完成定位和导航测试。
5. 若启用双机器人建图，两条轨迹进入同一验证坐标系；若不启用，配置和文档明确第二台机器人的用途。
6. 地图缺失或元数据错误时，`FinalizeTask1`拒绝导出。
7. 阶段切换、重复请求和节点重启不会产生两个有效`run_id`或互相矛盾的Manifest。
8. Task 1冻结后，地图和目标版本不可被静默覆盖，所有在线机器人均收到匹配阶段序号。

### P2必须完成的交接

- 与P1确认TF发布权、导航目标、恢复动作和探索速度。
- 与P3确认观测时间戳TF查询和地图修正时目标如何更新。
- 与P4确认冻结地图标识及Task 2定位就绪条件。
- 与P3确认目标版本、LLM原始输入输出和需要持久化的模型元数据。
- 与P5确认里程碑证据、发布清单和独立回放步骤。

## 4. P3——视觉感知、目标融合与本地LLM负责人

### 核心目标

把相机图像转换成准确、去重、可追溯的目标列表，并在边缘设备上把自然语言安全转换成候选`MissionPlan`。

### P3负责

- 相机内参、外参、图像时间戳和光学坐标系校验。
- ArUco字典、标记尺寸、检测、ID映射、目标类型和相对位姿估计。
- 发布机器人局部`TargetObservation`。
- 在观测时刻将目标变换到`map`。
- 多帧、多机器人目标关联、异常值剔除和融合。
- 目标协方差、置信度和重复目标合并策略。
- 权威`/edge/targets`目标注册表及其版本号。
- 按`docs/marker_and_rescue_geometry.md`的坐标约定，根据带版本的几何规则从标记位姿计算普通/协同救援区。
- Task 1目标JSON导出、Schema验证和感知评测数据集。
- 本地离线LLM运行环境、模型打包、Prompt和版本管理。
- 自然语言到候选`MissionPlan`的结构化转换，并调用`/edge/validate_mission`提交候选计划。
- 为每条指令发布`/edge/mission_intake`（原始指令、模型/Prompt版本、模型原始输出、结论和原因）。
- 对格式错误、虚构目标或无法稳定结构化的模型输出执行安全拒绝。
- 保存原始指令、模型版本和原始结构化输出，交由P2统一持久化。

### P3不负责

- 决定探索路线、机器人分配或救援顺序。
- 与救援区无关的Nav2控制器容差。
- 验证任务依赖图或调度任务；该职责属于P4。
- 选择具体机器人、路径或速度。

### P3的输入与输出

输入：P1的图像、CameraInfo、相机TF和时间同步；P1/P2的观测时刻全局TF；官方ArUco及救援区参数；P2的阶段和冻结状态；组织方自然语言及模型/硬件限制。

输出：原始`TargetObservation`、去重`TargetArray`、被拒观察的原因/统计、救援位姿、通过Schema校验的`targets.json`，以及候选`MissionPlan`或明确的解析拒绝原因。

### P3验收条件

1. 测试覆盖不同距离、角度、模糊和重复观察。
2. 使用带真值的小型数据集测量位置误差和协方差，不能只凭视觉判断。
3. 同一台或不同机器人的重复观察最终只有一个目标条目。
4. TF缺失、过期或外推失败时，不得伪造地图坐标目标。
5. 未知marker ID不得静默成为可得分目标。
6. Task 1冻结时只设置一次基本救援资格，Task 2新发现目标不能追溯获得资格。
7. 救援区只能由带版本的官方几何配置生成。
8. 本地模型能够断网运行，并覆盖顺序、并行、多重依赖、未知目标、歧义和不可结构化指令测试集。
9. P3只生成候选计划；未经P4验证的计划不得触发任何机器人动作。

### P3必须完成的交接

- 与P1确认标定、光学坐标系、时间戳和图像QoS。
- 与P2确认地图坐标、TF时间和回环修正影响。
- 与P4确认目标更新、置信度和救援区语义。
- 与P2确认JSON格式、模型元数据、日志和规则版本的持久化。
- 与P4确认候选计划字段、拒绝原因以及Schema/DAG验证反馈。
- 向P5提供感知评测和离线模型复现证据。

## 5. P4——多机器人协调、任务图验证与救援执行负责人

### 核心目标

验证P3生成的候选任务图，根据冻结目标和实时机器人状态确定机器人分工，稳定完成普通及双机器人协同救援。

### P4负责

- 边缘端机器人状态注册表和离线/过期判断。
- 根据Task 1冻结列表生成Task 2任务。
- 分配代价、机器人选择、协同配对和失败后的重新分配。
- Task 2A和Task 2B共用的依赖调度器。
- `/edge/validate_mission`服务：`MissionPlan` Schema、目标ID、能力、依赖环和可执行性验证；作为`/edge/mission_plan`唯一发布方。
- `/edge/mission_state`步骤执行状态。
- 无效、矛盾、循环或不可执行计划的安全拒绝，并给出机器可读原因。
- 协调层面的路径/资源冲突策略。
- 普通救援和协同救援状态机。
- 救援区占用判断、同步条件和连续停留计时；`/edge/rescue_verifier`是完成判定的唯一权威。
- Task 2A全部完成或Task 2B计划全部完成时，以`REQUESTER_SYSTEM`请求结束阶段。
- 取消、超时、重试、阻塞和失败语义。
- 权威`RescueTask`状态和只追加的`RescueEvent`事件流。
- Task 2A结束条件及全机器人安全冻结协调。

### P4不负责

- 直接发送电机速度或实现Nav2控制器。
- 估计ArUco目标坐标。
- 从自然语言生成任务依赖关系。
- 比赛过程中手工修改错误的LLM结果。

### P4的输入与输出

输入：P3冻结的`TargetArray`、救援位姿及候选`MissionPlan`，P1的机器人状态和动作服务器，以及P2的阶段/计时参数。

输出：有效`MissionPlan`或明确拒绝、`RescueTask`、机器人动作目标/取消、进入救援区/开始停留/重置/完成/失败事件，以及每个Task 2B步骤的等待、可执行、完成或阻塞状态。

### P4验收条件

1. 普通任务只获得一次基本完成，可在机器人失败后重新分配。
2. 协同任务始终使用两台不同机器人和两个不同救援区。
3. 只有两台机器人同时满足条件时累计协同停留时间；任意一台离开立即清零。
4. 重复消息或节点重启不会重复计分。
5. 状态过期、未定位或严重故障机器人不得参与分配。
6. 无依赖任务可以并行；所有前置任务完成前后继任务不可启动。
7. 阶段冻结会取消运动并收集所有在线机器人的安全状态确认。
8. Schema错误、未知目标、循环依赖或能力不满足的计划无法进入调度器。

### P4必须完成的交接

- 与P1确认执行动作、健康状态、取消和救援区状态。
- 与P2确认地图冻结和重定位就绪。
- 与P3确认目标可变范围及救援几何。
- 与P2确认事件落盘、阶段冻结、计时参数和回放语义。
- 与P3确认候选任务图语义及验证错误反馈。
- 向P5提供普通、协同和Task 2B执行的独立验收证据。

## 6. P5——接口治理、独立验证与发布负责人（轻量角色）

### 核心目标

维护共享契约并独立检查里程碑证据，确保P1～P4的成果能够形成可复现发布版本，但不承担比赛运行时生产功能开发。

### P5负责

- `edgeai_robot_interfaces`版本、兼容性和变更记录治理。
- 接口生产方/消费方审核清单以及Schema版本迁移检查。
- CI入口、系统测试框架和里程碑验收报告；具体模块测试由P1～P4实现。
- 从干净终端独立执行P1～P4提供的构建、回放和验收命令。
- 发布清单、发布标签、最终提交包及可恢复性检查。
- 架构索引、比赛运行手册和官方规则TBD登记；技术内容由对应负责人提供。
- 汇总缺陷、指定到对应负责人并复核修复证据，不代替负责人修复生产模块。
- 官方和中期参数及真值文件（目标坐标、半径、标记ID与类型、尺寸、起始区、停留时间）的录入和版本管理；各模块只从该文件读取（第11节G3）。
- 里程碑和中期检查的结果验证材料：汇总P2～P4产生的地图、检测证据、距离历史、完成标志、计时和碰撞记录，形成规定时间内可展示的材料，并维护对应运行手册（第11节G10）。
- 与组织方沟通规则疑问和场地修改，并把答复写回TBD登记表（第11节G11）。

### P5不负责

- 实现或维护导航、SLAM、感知、LLM、任务调度、阶段管理和日志等生产节点。
- 为P1～P4代写其模块测试、配置或使用说明。
- 承担日常跨模块调试的唯一责任；接口两端负责人必须先共同定位。
- 没有模块负责人证据就宣布模块正确，或绕过失败验收直接发布。

### P5的输入与输出

输入：P1～P4提交的接口变更、测试证据、运行记录、版本信息和官方规则来源。

输出：接口版本与变更记录、独立验收报告、未解决缺陷清单、发布标签及最终提交包。

### P5验收条件

1. 共享接口能够构建，兼容性或迁移影响有明确记录。
2. CI能调用P1～P4提供的模块测试和协议检查，失败时明确归属模块。
3. 能在干净环境按运行手册构建并启动当前比赛配置。
4. 官方TBD值都能追溯到来源、版本、日期和受影响负责人。
5. 发布候选包含配置、模型、组件、Git版本、依赖和已知问题清单。
6. 独立复核确认Task 1、Task 2A和Task 2B回放与Manifest一致。

### P5必须完成的交接

- P1～P4必须提交可重复命令、正常/失败样例、已知限制和负责人签字。
- P5在约定审核时限内返回“通过”或带归属人的缺陷清单，不接管生产代码修复。
- P5与P2确认发布包、Manifest和回放材料，与P3/P4确认任务计划接口版本。

## 8. 必须共同批准的修改

- Topic、TF或命名空间：P1、所有受影响生产者/消费者；涉及共享接口时加入P5。
- 地图坐标或地图融合：P1、P2、P3。
- 目标格式或救援几何：P3、P4、P5。
- 救援任务状态机：P1、P4、P5。
- LLM任务计划格式：P3、P4、P5。
- 比赛阶段、冻结和持久化：P1、P2及受影响模块负责人；发布时由P5复核。
- 得分证据：受影响模块负责人、P2；里程碑发布时由P5独立复核。
- 官方比赛参数：P5先记录来源、版本和日期，再由受影响负责人审核。

发生分歧时，以当前官方规则和可测试的验收条件为准。未解决分歧必须记录，不允许不同模块私下使用同名但不同语义的字段。

## 9. 团队协作节奏

- 每周开始：每人提出一个可测量集成结果及需要他人提供的输入。
- 每日同步：重点报告接口阻塞和共享测试失败，不罗列工作时长。
- 每周至少两次：使用共享仿真场景集成。
- 每周结束：跑一次当前完整关键链路并保存日志。
- 每个里程碑前：由非负责人按照模块说明从干净终端重新验证。

## 10. 模块交接清单

任何生产者向消费者交付接口时，必须同时提供：

1. 精确Topic/Action/Service及消息版本。
2. 坐标系、时间戳、单位、QoS、频率和延迟预期。
3. 一个正常样例和至少一个错误/失败样例。
4. 启动依赖和就绪判断。
5. 数据过期、节点重启和重复消息行为。
6. 主负责人和备份负责人。
7. 自动化或可重复的验收命令。
8. 与上一版本相比的语义变化说明。
