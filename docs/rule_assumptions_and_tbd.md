# 比赛规则假设与TBD登记表

已审核来源：`Edge_AI_Robotics_Challenge_Rulebook_V0.md`。

本文档严格区分“组织方规则”和“团队开发默认值”。开发默认值不代表官方要求。收到新规则后，应记录版本、日期和来源，并在修改比赛配置前让所有受影响负责人完成审核。

## 1. 当前草案中已经确认的设计约束

- Task 1可使用一台或两台机器人，最终必须输出一张统一地图和一份统一目标列表。
- Task 2最多可使用四台机器人；协同救援必须使用两台不同机器人。
- 计时期间，探索、目标选择、导航、机器人分配和救援执行必须自主完成。
- 操作员可以启动系统、监控状态、提交组织方指令、请求重置和触发急停；不得遥控机器人或人工修复算法输出。
- Task 2基本救援分数只适用于Task 1结束时已经冻结到目标列表中的目标。
- LLM只作为高层任务解释器，不得控制底层运动或直接分配机器人。
- 必须保存与目标、机器人、任务、LLM和实际执行有关的得分证据。
- 通信中断时，机器人必须执行预先定义的安全行为。

## 3. 需要组织方书面澄清的规则冲突

### Task 2A到Task 2B是否重新摆放机器人

- 第4章暂定规则写明：Task 2A和Task 2B之间原则上不重新摆放机器人，安全原因除外。
- 第6.5节写明：Task 2A结果确认后，组织方会把机器人移动到预定义的Task 2B起点。

当前工程决策：同时支持两种流程。进入`FROZEN`后，阶段管理器允许执行可配置的重新定位和就绪检查；任何代码都不能假设Task 2A与Task 2B之间位姿连续。

### 本地LLM还是外部云端LLM

- 第6.6节写有“本地（或外部云端，TBD）”。
- 第7.2节要求本地推理，并暂定禁止在正式计时中使用外部云端AI。

当前工程决策：比赛关键路径按照完全本地、断网可运行设计。任何云服务都不能成为运行依赖。

## 4. 团队开发假设

以下内容属于团队工程选择，不是比赛规则：

- 机器人标准ID为`robot_1`～`robot_4`。
- 边缘节点维护权威目标注册表和任务注册表。
- Nav2隐藏在机器人执行动作之后，边缘协调器不直接调用Nav2。
- 持久化目标和任务计划使用JSON，并包含明确的Schema版本。
- 事件日志使用只追加的JSON Lines格式。
- 所有规则参数和TBD值从`config/competition_parameters.yaml`加载，并按运行模式统一解析。
- 救援区占用和停留计时只由边缘验证器判定；机器人只负责到达并保持。
- 自主模块可以请求结束当前阶段（探索完成、Task 2A全部完成），对应规则5.5“队伍宣布完成”和6.5第2条。

## 5. 规则更新检查清单

组织方发布新版本后，应执行：

1. 保存原始文件，记录版本和生效日期。
2. 与当前已审核规则逐项比较。
3. 更新本登记表，确定受影响的接口和配置。
4. 按职责文档获得相关负责人的审核。
5. 更新官方配置值，不覆盖开发历史。
6. 运行受影响的单元测试、集成测试和端到端测试。
7. 在发布包和运行Manifest中记录规则及配置版本。
